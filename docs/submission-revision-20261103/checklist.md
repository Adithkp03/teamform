## Implemented and tested
- **Team rules:** min/max size; forming state; one team per person enforced by database uniqueness; expiring/rotatable invite code; leader transfer on departure; final member departure deletes the team.
- **Race proof:** 50 concurrent joins for 1 remaining seat: 1 success, 49 clean 409s, checked final count 4. Eight concurrency tests also cover concurrent accepts, two-team races, idempotent retries and leader departure.
- **Leader decisions:** server-side accept/decline/remove permissions, locked nonpending-request rejection, actor/subject audit history. UI alone is not the permission boundary.
- **Invitations:** leaders invite people from the board or suggestions; one pending invite per (team, invitee) enforced by a partial unique index; invitee-only accept/decline, leader-only withdraw, requester cancel of their own join request; invite events stay private to the invitee over SSE in both poll modes. Pending invitations expire 7 days after creation (migration 0015): expired invites leave the inbox and the team's pending list, and accepting one is refused (`invitation_expired`), cancelled and audited.
- **Auth/identity:** Firebase Authentication (Spark, no card) with server-side Google verification of every ID token, `email_verified` enforced server-side, uid-bound encrypted Firebase-refresh-token storage for revocation at rotation, legacy bcrypt sign-in retained, and legacy claim gated on password/session plus verified Firebase identity. Dev login and the offline token seam fail the deploy loudly if ever enabled in production.
- **Retries:** exact keyed routes are create-team, join-by-code, create-request and rotate-invite. Response-loss replays return the identical stored response; a stored 4xx replays after the race resolves; a stale (>60s) in-flight key is taken over by the retry. Accept/decline are locked state transitions, leave/remove retry-safe deletes, profile last-write-wins.
- **Live board/team:** SSE plus shared ~1s poller in production; production two-browser observations documented in the requirement audit. Not a latency guarantee.
- **Suggestions:** grounded per-candidate reasons from the same stored fields the score uses, labelled a transparent heuristic; serves recorded as impressions and per-suggestion useful/not votes collected so ranking quality is measured (organizer funnel: serves, join-within-7d upper-bound proxy, vote split); votes are accepted only for candidates actually served to the voter (impression-checked, 404 otherwise), so the metrics cannot be polluted by fabricated votes. Timezone scoring is DST-safe: offsets are derived live from each profile's IANA zone name (Postgres tz database) at query time; the stored numeric offset is only a fallback for unrecognized zone names and is re-derived on every profile save.
- **Board:** server-side search + skill/timezone/capacity/looking filters persistent through cursor pagination (timezone now applies to team cards too); min-open-seats filter; 24-card pages; truncated counts say 24+; stale-response sequence guard on refresh AND load-more. The shared 1s board cache carries public board data only: the viewer's own pending-request state is merged per-request after the cache read, so a warm cached page can never serve one participant's request state (or request id) to another. The join-request card shows a cancelable 'Request pending' only when the server confirms an existing pending request (`request_already_pending` or the board's own `my_pending_request_id`) - conflicts like team_full/already_in_team restore the button instead of a phantom pending.
- **Organizer operations:** fail-closed allowlist (`ORGANIZER_EMAILS`) + verified-email requirement (an unverified account with an allowlisted address gets nothing - regression-tested). Event settings with audited before/after + over-cap report; audit search/CSV export surviving team deletion (the console pages the full trail with cursor-based 'Load more audit rows'; CSV export is a single status-checked request so an error page can never be saved as a CSV) (manual audit retention policy: event + 90 days, export before cleanup, audit rows never auto-deleted; growing operational tables are pruned by an organizer-run audited sweep endpoint, dry-run by default, with per-sweep counts in the audit log and a queryable last-sweep time - the sweep bounds growth only when the organizer runs it, it is not automatic); stuck-request cancel-with-reason (no operator force-accept); matching funnel.
- **Observability:** `x-request-id` on every response + structured error logs; `/api/metrics` (organizer-only) with per-route latency histograms, DB pool occupancy, live SSE clients - plus durable 5-minute per-route rollups (14-day retention, pruned on flush; route templates only, no IDs/PII) aggregated across serverless instances, with a 24h durable view on the same endpoint - serverless flush is best-effort (interval + ~1% of responses + metrics reads), so recent minutes can lag; durable history, not exact complete observability; scheduled 15-min GitHub Actions health monitor (alerting is GitHub's native failure notification; the workflow sends nothing itself); incident/recovery runbook in `docs/operations.md`.
- **Privacy:** participant-facing notice on profile + suggestions pages (name/skills/timezone visible to signed-in participants while looking; suggestion serves and votes recorded WITH the account, visible only to allowlisted organizers as aggregate counts; impressions self-prune automatically once older than 30 days as suggestions are served); self-serve `GET /api/me/export` (explicit columns, no credential material); account deletion is organizer-assisted by design, not self-serve (seat/leadership safety). NB: the allowlisted organizer account must verify its email before the console admits it (fail-closed guard).
- **Onboarding:** first-run checklist on the board (complete profile, join/create, suggestions) driven by the server profile/team state.
- **UI:** light blue/white theme, responsive navigation/cards, labeled forms, visible focus, 44px touch targets. 320/390px widths, 200% zoom (CSS zoom emulation in the spec), and keyboard-only full flow covered by specs. Profile Save waits for initial load; failed form input is preserved with inline errors.
- **Security defaults:** production-like boot refuses to start without CORS_ORIGIN (fail-closed); nosniff/frame-deny/no-referrer/default-deny-CSP headers on every API response; rate-limit buckets and idempotency records self-prune.
- **Verification:** 172 API tests / 19 files on a fresh migration-only DB, 13 browser tests; axe scan reports no serious/critical violations on scanned pages, plus a 390px ARIA-semantics pass (naming, aria-pressed) - semantics verification, not VoiceOver/TalkBack. Chaos is 1 crash-recovery drill / 6 invariants, not 6 tests. Integrity fix: earlier hosted chaos runs passed vacuously (broken compose build context since the initial commit + missing `pipefail` masked the failures); this revision repairs the pipeline and asserts the storm reached the API; the repaired drill then caught a real boot regression on an intermediate push, and the deployed SHA's run is a verified real pass.

## Open limits: do not call these done
- **Real-inbox receipt owner-verified for verification mail; reset mail unexercised.** Firebase sends verification/reset mail and the exchange is proven against real Google-signed tokens; the new organizer account's verification mail reached the owner's real inbox and was confirmed 3 Nov 2026 (server-side email_verified_at set). Password-reset mail receipt remains unexercised. Free-tier mail can land in spam.
- **Full legacy->Firebase claim with a verified identity remains incomplete, and is superseded for organizer access.** Proven on production: an unverified Firebase identity is refused 403 at the claim gate, and legacy password sign-in/session works (synthetic account, cleaned up). The completed verified claim was never exercised; the legacy profile is left untouched, and organizer access instead runs on a new verified Firebase account added to the organizer allowlist (email-verified guard unchanged; anon/non-allowlisted organizer routes re-verified 401/403 on the live 93e9a09 deployment).
