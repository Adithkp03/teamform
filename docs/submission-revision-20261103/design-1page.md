# CrewForge - design and evidence
Adith K P · 3 Nov 2026 · product-hardening revision · public repository

**App:** https://teamform-web.vercel.app · **Repo:** https://github.com/Adithkp03/teamform

## Correctness at the database
Fastify/TypeScript + Postgres, React/Vite. One hackathon per deployment; min/max team sizes, expiring/rotatable invites, leader approval, explained suggestions and audit history. `UNIQUE(hackathon_id,user_id)` enforces one team per person. Join/accept lock the team row in a transaction, count actual memberships under that lock, then insert. A 50-way race for one seat yields 1 winner/49 clean 409s; the checked final membership count stays 4. Leader-to-person invitations mirror join requests: a partial unique index allows one pending invite per (team, invitee), leaders create/withdraw, invitees accept/decline, all through the same locked seat invariants, and requesters can cancel their own pending join request. Seed users have no password login.

## Identity: Firebase Authentication
Sign-in is Firebase email/password on the free Spark tier (no card). Firebase itself sends verification and password-reset email. The client exchanges its Firebase ID token **and** refresh token at `/api/auth/firebase`; the server verifies the ID token against Google (signature, issuer, audience, expiry), requires `email_verified` in the verified token, and requires the presented refresh token to redeem to the same uid before storing it AES-256-GCM-encrypted for revocation checks at app-token rotation (a Firebase password reset/change kills the app family at its next rotation). Legacy bcrypt accounts keep working; claiming one needs the legacy password or an authenticated legacy session plus the verified Firebase identity - never email equality alone. Dev login and the offline token seam are refused at boot in any production-like env.

## Retry and event semantics
Idempotency keys cover create-team, join-by-code, create-request and invite-rotate, replaying stored responses - including response-loss replays and stale-worker (>60s) takeovers, both tested. Accept/decline use a locked state transition; repeated nonpending decisions return 409. Leave/remove are retry-safe deletes. A transactional event table and audit row commit with each change. Production SSE uses a shared per-process ~1s poller, rotating streams at 280s and resuming by event ID. Poll interval is not a delivery guarantee.

## Reads, pagination and matching
Board payload has no invite codes or requests. Auth precedes each cache access. In-process 1s TTL cache, bounded 32 keys, generation guard; local mutations invalidate after commit. The cached payload is public board data only - the viewer's pending request state is merged per-request after the cache read into fresh row objects, so a warm page can never serve one participant's request id to another. Cursor pagination implemented. Search plus skill/timezone/capacity/looking filters run **server-side** and persist through pagination; the timezone filter now also applies to team cards via the projected leader timezone. Board cards carry the viewer's pending request id, so pending state survives a refresh, and a request-sequence guard discards stale board responses on both refresh and load-more (the old immediate + debounced double-fetch race is removed). The join-request card shows a cancelable pending state only on server-confirmed existing requests; conflicts (team full, already on a team) restore the request button. Suggestion timezone distance is circular on clock time, so UTC-12 against UTC+14 reads as 2 hours apart, not 26. Scoring derives each profile's offset live from its IANA zone name (Postgres tz database), so DST transitions never drift the score; the stored numeric offset is only a fallback for unrecognized zone names, and the profile write path re-derives it from the zone name on every save. Suggestions show grounded per-candidate reasons derived from the same stored fields the score uses, and are labelled a transparent heuristic: every serve is recorded as an impression and users vote useful/not, so ranking quality is measured (join-within-7d upper-bound proxy + vote split), not asserted; votes are accepted only for candidates the voter was actually served (impression-checked), so the metrics cannot be stuffed.

## Organizer operations and observability
Allowlisted organizers (`ORGANIZER_EMAILS`; unset = nobody, and a VERIFIED profile email is required - an unverified account holding an allowlisted address gets nothing) get a web console plus API: event settings with audited before/after and an over-cap report, audit search + CSV export that survives team deletion, stuck-request resolution as cancel-with-audited-reason (force-accept deliberately absent; operators never override seat invariants), and the matching funnel. Audit retention remains a manual policy (event + 90 days, export before cleanup; audit rows are never auto-deleted), and the operational tables that DO grow are pruned by an organizer-run, audited sweep (`POST /api/organizer/retention/sweep`, dry-run by default; expired auth artifacts, stale rate-limit/idempotency windows, dispatched domain events past the SSE replay window, old suggestion impressions and metric rollups; each sweep writes an audit row with per-table counts and the last sweep time is queryable), so free-DB growth is bounded once the organizer runs it - the sweep makes the policy performable and tracked, it does not run itself. Every response carries `x-request-id`, echoed on error logs; `/api/metrics` is organizer-only and exposes per-route latency histograms, DB pool occupancy and live SSE client count; the per-route counters also flush into durable 5-minute rollups (14-day retention, pruned on every flush; route keys are templates like `/api/teams/:id`, never concrete IDs), aggregated across serverless instances, with the last 24h returned alongside the live snapshot; on serverless the flush is BEST-EFFORT (a 60s interval on the long-running server, ~1% of responses, and every metrics read), so recent minutes can be missing until the next flush - durable history, not exact complete observability; a scheduled GitHub Actions monitor pings production every 15 minutes and GitHub's native failure notification emails the owner (the workflow itself sends nothing). Incident and recovery recipes: `docs/operations.md`.

Participant privacy: display name, skills and timezone are visible to signed-in participants while someone is looking for a team; suggestion serves and useful/not-useful votes are recorded WITH the account (never claimed anonymous) and visible only to allowlisted organizers as aggregate counts, and suggestion impressions self-prune automatically once older than 30 days as suggestions are served (probabilistic sweep built into the serve path, with the organizer retention sweep as backstop). The profile page states this plainly and offers a self-serve JSON export of everything stored about the caller (`GET /api/me/export` - explicit columns, no credential material). Account deletion is deliberately NOT self-serve - removing a profile mid-event can trap team seats and leadership, so it is an organizer-assisted, effects-reviewed decision. Verified post-migration against production with a controlled synthetic fixture (invite accept, request decline, impressions written, export 200), then fully cleaned; the allowlisted organizer account must complete email verification before the console will admit it - the fail-closed guard working as intended.

## Session security
15-min access JWTs; opaque hashed refresh tokens with family rotation, 30-day absolute family expiry, fixed 10s grace, family liveness and replay revocation. Firebase credential validity is re-proven before rotation; a Google outage yields a state-preserving 503, an invalid credential revokes the family. zod validation, leader-only server guards, per-IP/identity rate limits, origin-pinned CORS. CORS now fails closed: a production-like boot without an explicit CORS_ORIGIN is refused, and every API response carries nosniff, frame-deny, no-referrer and a default-deny CSP. Rate-limit buckets and idempotency-key records self-prune so free-tier memory and database stay bounded.

## Limits and next work
Free Vercel Hobby + Neon free + Firebase Spark; caps/cold starts remain; free-tier mail can land in spam. Real-inbox receipt is now owner-verified for Firebase verification mail: the new organizer account's verification mail reached the owner's real inbox and was confirmed 3 Nov 2026 (server-side email_verified_at set). Reset-mail receipt remains unexercised, and the full legacy->Firebase claim with a verified identity stays incomplete - superseded for organizer access by the new verified Firebase account, added to the organizer allowlist with the email-verified guard unchanged. No durable app-level mail queue or 10k-mail simulation. Single-event scope remains (the schema keys every entity by hackathon_id already, so multi-event is an additive migration path, not a rewrite - but enrollment UX, per-event scoping of the board/suggestions and organizer tooling per event are product decisions for the owner, not safe silent increments) - next: enrollment/scoped board as a deliberate product step, outcome-calibrated scoring once feedback data exists, rate-limit headers. No paid plan/domain/card or organizer submission.
