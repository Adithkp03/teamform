# TeamForm - design and evidence
Adith K P · 3 Nov 2026 · product-hardening revision · public repository

**App:** https://teamform-web.vercel.app · **Repo:** https://github.com/Adithkp03/teamform

## Correctness at the database
Fastify/TypeScript + Postgres, React/Vite. One hackathon per deployment; min/max team sizes, expiring/rotatable invites, leader approval, explained suggestions and audit history. `UNIQUE(hackathon_id,user_id)` enforces one team per person. Join/accept lock the team row in a transaction, count actual memberships under that lock, then insert. A 50-way race for one seat yields 1 winner/49 clean 409s; the checked final membership count stays 4. Leader-to-person invitations mirror join requests: a partial unique index allows one pending invite per (team, invitee), leaders create/withdraw, invitees accept/decline, all through the same locked seat invariants, and requesters can cancel their own pending join request. Seed users have no password login.

## Identity: Firebase Authentication
Sign-in is Firebase email/password on the free Spark tier (no card). Firebase itself sends verification and password-reset email. The client exchanges its Firebase ID token **and** refresh token at `/api/auth/firebase`; the server verifies the ID token against Google (signature, issuer, audience, expiry), requires `email_verified` in the verified token, and requires the presented refresh token to redeem to the same uid before storing it AES-256-GCM-encrypted for revocation checks at app-token rotation (a Firebase password reset/change kills the app family at its next rotation). Legacy bcrypt accounts keep working; claiming one needs the legacy password or an authenticated legacy session plus the verified Firebase identity - never email equality alone. Dev login and the offline token seam are refused at boot in any production-like env.

## Retry and event semantics
Idempotency keys cover create-team, join-by-code, create-request and invite-rotate, replaying stored responses - including response-loss replays and stale-worker (>60s) takeovers, both tested. Accept/decline use a locked state transition; repeated nonpending decisions return 409. Leave/remove are retry-safe deletes. A transactional event table and audit row commit with each change. Production SSE uses a shared per-process ~1s poller, rotating streams at 280s and resuming by event ID. Poll interval is not a delivery guarantee.

## Reads, pagination and matching
Board payload has no invite codes or requests. Auth precedes each cache access. In-process 1s TTL cache, bounded 32 keys, generation guard; local mutations invalidate after commit. Cursor pagination implemented. Search plus skill/timezone/capacity/looking filters run **server-side** and persist through pagination; the timezone filter now also applies to team cards via the projected leader timezone. Board cards carry the viewer's pending request id, so pending state survives a refresh, and a request-sequence guard discards stale board responses (the old immediate + debounced double-fetch race is removed). Suggestion timezone distance is circular on clock time, so UTC-12 against UTC+14 reads as 2 hours apart, not 26. Suggestions show grounded per-candidate reasons derived from the same stored fields the score uses, and are labelled a transparent heuristic: every serve is recorded as an impression and users vote useful/not, so ranking quality is measured (join-within-7d upper-bound proxy + vote split), not asserted.

## Organizer operations and observability
Allowlisted organizers (`ORGANIZER_EMAILS`; unset = nobody, and a VERIFIED profile email is required - an unverified account holding an allowlisted address gets nothing) get a web console plus API: event settings with audited before/after and an over-cap report, audit search + CSV export that survives team deletion, stuck-request resolution as cancel-with-audited-reason (force-accept deliberately absent; operators never override seat invariants), and the matching funnel. Retention is a manual policy (event + 90 days, export before manual cleanup; no automatic deletion - suggestion impressions and votes are covered by the same policy, so the free database does not grow without bound). Every response carries `x-request-id`, echoed on error logs; `/api/metrics` is organizer-only and exposes per-route latency histograms, DB pool occupancy and live SSE client count - per-instance, in-process and non-durable (cold starts reset it, serverless instances are not aggregated); it is an operator signal, not durable telemetry; a scheduled GitHub Actions monitor pings production every 15 minutes and GitHub's native failure notification emails the owner (the workflow itself sends nothing). Incident and recovery recipes: `docs/operations.md`.

## Session security
15-min access JWTs; opaque hashed refresh tokens with family rotation, 30-day absolute family expiry, fixed 10s grace, family liveness and replay revocation. Firebase credential validity is re-proven before rotation; a Google outage yields a state-preserving 503, an invalid credential revokes the family. zod validation, leader-only server guards, per-IP/identity rate limits, origin-pinned CORS. CORS now fails closed: a production-like boot without an explicit CORS_ORIGIN is refused, and every API response carries nosniff, frame-deny, no-referrer and a default-deny CSP. Rate-limit buckets and idempotency-key records self-prune so free-tier memory and database stay bounded.

157 API tests / 17 files on a fresh migration-only database; 13 browser tests (flows, realtime, keyboard, axe + ARIA-semantics incl. a 390px pass - not VoiceOver/TalkBack, 200% zoom (CSS emulation), onboarding, edge data). Hosted CI on the tested bundle `6b41a19`: test, e2e, chaos and k6 load all pass (CI test https://github.com/Adithkp03/teamform/actions/runs/41580838981, e2e https://github.com/Adithkp03/teamform/actions/runs/41580838910, chaos https://github.com/Adithkp03/teamform/actions/runs/41580838957 (log read: image built, 20-worker storm reached the API - ok=60, 373 expected conflicts, 367 transport failures at the kill - all 6 invariants PASS), k6 load https://github.com/Adithkp03/teamform/actions/runs/41580839032). Local full 10k-profile/2k-team seed: board p95 138-140ms at 100 readers, 0 failures. Historical 206.47ms mixed-load miss kept beside the passes in `docs/load-test-report.md`. **Production p95 unmeasured** - Vercel Hobby forbids load tests.

Chaos-drill integrity: every hosted chaos run before this revision passed vacuously - the compose build context had been broken since the initial commit and the publish step lacked `pipefail`, so a failed image build still produced a green checkmark. This revision fixes both (root build context with a real multi-stage web Dockerfile, `pipefail`, and an explicit assertion that the join storm actually reached the API). The chaos run on this SHA (https://github.com/Adithkp03/teamform/actions/runs/41580838957) is the first whose log was read to confirm the build and storm assertions genuinely executed; all earlier hosted chaos greens are superseded and count for nothing.

## Limits and next work
Free Vercel Hobby + Neon free + Firebase Spark; caps/cold starts remain; free-tier mail can land in spam. One owner-verified real-inbox receipt is still pending for the full migration claim. No durable app-level mail queue or 10k-mail simulation. Single-event scope remains; profiles store a numeric UTC offset that can drift across DST until re-saved (board filtering uses the timezone name and is unaffected; scoring distance can drift by an hour) - next: enrollment/scoped board, outcome-calibrated scoring once feedback data exists, rate-limit headers. No paid plan/domain/card or organizer submission.
