[01 - race, target45seconds]
Fifty people. One remaining seat. This is the failure case TeamForm is built to prevent. Here is the automated concurrency test, running against an isolated Postgres database. Exactly one join succeeds. The other forty-nine receive a clean conflict response. No extra member slips through. The team row is locked inside a transaction, the seat count is checked under that lock, and a database uniqueness rule enforces one team per person. This is tested behavior, not a claim that the public deployment can serve ten thousand simultaneous users.
[02 - lightboard, target35seconds]
The interface now uses light mode, with white cards, a blue accent, clear navigation and visible keyboard focus. Teams and people have separate views. Counts describe loaded results: a plus sign means there are more pages. Board search and the skill, timezone, capacity and looking-for-team filters run on the server and persist through pagination. Suggested teammates show grounded match reasons taken from the same stored fields the scoring uses. A first-run checklist guides new participants from profile to team. Invite-code join and team creation remain separate from discovery. On a phone, those actions move above the long list instead of getting buried at the bottom.
[03 - approval, target40seconds]
Now the leader approval flow. One participant creates a team. Another requests to join from the board. The leader sees the request, accepts it, and the membership count updates. The history shows who acted, who was affected, and when. Acceptance is authorized on the server, not merely hidden in the interface. A full team or a request that is no longer pending is rejected safely. Retried keyed operations replay their stored result instead of adding another team or membership.
[04 - twobrowser, target35seconds]
These are two separate browser sessions on the local test stack, not the same tab being refreshed. A new team appears on the other participant's open board. Requests and accepted membership changes update without reloading. The application uses server-sent events. In the hosted setup, a shared poller checks committed events roughly once a second. That interval is a design choice, not an end-to-end delivery guarantee. Previous production two-browser observations are recorded separately in the requirement audit.
[05 - keyboardmobile, target35seconds]
The same flow remains usable with a keyboard. Focus is visible, the skip link leads to the main content, and every form has labels. Saving a profile now waits for its initial data to load, so a late response cannot overwrite an edit. Automated browser checks cover the full team flow, keyboard navigation, two-session live updates, accessibility, search and final-page cursor handling. The layout also fits three hundred and twenty and three hundred and ninety pixel widths without page-wide horizontal scrolling.
[06 - evidence, target45seconds]
For scale, the dataset contains ten thousand synthetic profiles and two thousand teams. The board test uses one hundred concurrent readers. The mixed scenario uses ninety-nine readers and four paced mutators. These are isolated tests, not production traffic. The report keeps distinct runs and commit labels. One mixed run missed the two hundred millisecond target at two hundred and six point four seven milliseconds. An identical application later passed at thirty-six point two. The optimized build passed at forty-seven point two eight. That variation does not prove a causal speed improvement. The latest completed workflow is shown here with its own result, not assigned an older run's measurement.
[07 - limits, target30seconds]
The repository is public. Cursor pagination is implemented, so the design document no longer lists it as future work. The checklist and design now agree with the code. Production latency remains unmeasured, and production load testing has not been performed. Sign-in now runs through Firebase Authentication on the free Spark tier: Firebase sends the real verification and password-reset emails, and the server verifies every Firebase token against Google before issuing app sessions. Existing password accounts keep working and can be migrated by proving the old password or session plus the verified Firebase identity. End-to-end inbox receipt is owner-verified, and free-tier mail can land in spam. There is still no durable app-level email queue or ten-thousand-email simulation to claim. The project stays on free tiers, with no paid sender, domain purchase or organizer submission. That is the current, honest boundary of this demo.
